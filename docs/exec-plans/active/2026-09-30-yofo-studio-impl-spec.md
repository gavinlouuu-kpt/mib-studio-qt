# YOFO Studio implementation spec — application side

Status: proposed, 2026-09-30. Parent plan: [2026-09-30-yofo-studio-pz7035](2026-09-30-yofo-studio-pz7035.md)
(work packages W1-W8). Decision: [ADR 0008](../../decisions/0008-yofo-studio-pl-instrument.md).
Board-side spec: pz7035-imx426 `docs/platform/YOFO_IMPL_SPEC.md` (ABI 1.2, producer, driver, PL, Yocto).

Conventions: paths are on `dev/react-tauri`. "Fixture" = a byte-exact file generated by the board
repository's ABI generator (`abi/generated/fixtures/`), pinned by hash in this repository. Every
item lists its tests and its exit evidence; the evidence class vocabulary is the E0 manifest's.
Effort figures are rough engineer-weeks for one person, for sequencing only.

## S1. Execution-provider seam (E3 #447) — 3 weeks

**Interface** `include/backend/processing/IExecutionProvider.h` (new, Qt-free, C++17 value types):

```cpp
namespace backend::processing {
struct ProviderCapabilities { uint16_t scienceProfile, profileVersion; uint32_t limitResults,
    parameterPageWords; bool hasStore, hasTriggerOutput, hasPreviewDma; std::array<uint8_t,16> profileId; };
struct ProviderRunConfig { CompiledProfile profile; uint64_t runId; StorePolicy store; };
struct ProviderFrame { uint64_t frameId, timestampTicks; uint32_t epoch, flags; uint16_t width, height;
    std::vector<FilterResult> objects; std::optional<TriggerEvent> event; };
class IExecutionProvider {
public:
    virtual ~IExecutionProvider() = default;
    virtual ProviderCapabilities capabilities() const = 0;
    virtual CommitOutcome commit(const CompiledProfile&, uint32_t epoch, std::chrono::milliseconds wait) = 0;
    virtual void uploadTable(TableId, std::span<const uint8_t>) = 0;      // BACKGROUND, EMODULUS_LUT
    virtual StartOutcome arm(uint64_t runId) = 0;  virtual void stop(std::chrono::milliseconds drain) = 0;
    virtual void setSink(std::function<void(ProviderFrame&&)>) = 0;      // called from the provider thread
    virtual ProviderStatus status() const = 0;                             // state, fault, counters[16]
};
}
```

**Implementations**
- `PzMibExecutionProvider` (`src/backend/processing/pz/`, Linux only, built when
  `MIB_ENABLE_PZ_MIB=ON`): opens `/dev/pz_mib0`, ioctls per `driver/include/uapi/pz_mib.h`
  (`GET_IDENTITY`, `SET_CONFIG` with `PZ_MIB_CONFIG_WAIT`, `CONTROL`, `GET_STATUS`; ABI 1.2 adds
  `SET_PROFILE_PAGE`, `LOAD_TABLE`), one reader thread on `read()`/`poll()` that parses records with
  the generated decoder and groups RESULT/EVENT records under their FRAME by `frame_id`.
- `ReplayExecutionProvider` (all platforms): replays record fixtures at a scheduled rate; the E0
  rule that tests never need hardware.
- Selection: `MIB_EXECUTION_PROVIDER=host|pz|replay` read in `AppBackend.cpp` next to
  `MIB_CAMERA_MODE`; `host` keeps `realtimeInlineLoop`.

**Record decoder** `src/backend/processing/pz/PzRecords.{h,cpp}`: generated from the board
repository's `abi/pz_mib_abi.json` (header layout, record types, flags, counters) by a script vendored
here (`scripts/gen_pz_records.py`), with the source JSON hash pinned in `PzRecords.h`; profile-1
payload (16 words, layout in the board spec) decoded into `FilterResult` with the fixed-point
conversions (Q16.16, Q0.16, Q8.8) and `youngsModulus = NaN` when `EMOD_OUT_OF_COVERAGE`.

**Integration into `ProcessingService`**: a new entry `ingestProviderFrame(ProviderFrame&&)` that
feeds exactly what `realtimeInlineLoop` feeds after metrics: monitoring rows
(`BridgeMonitoringRow`), `ProcessingResultEvent`, the identification funnel and reason histogram
(computed on the PS from RESULT flags: reason code [7:4], UNSERVED = TARGET results without an
EVENT), `noteTargetLatency` from `EVENT.latency_ticks / timestamp_hz`, autofocus samples
(`ringRatio` of valid objects), and the experiment metadata path (S3). The inline thread is not
started when a provider is active; `FrameStore` is fed only by the preview camera.

**Tests**: `processing.provider_replay_rows` (fixtures -> rows equal to a golden JSON),
`processing.pz_records_decode` (every fixture record type, CRC, flags), `processing.provider_funnel`
(reason histogram and UNSERVED from a synthetic stream), TSan on the sink hand-off.
**Exit**: replay provider drives a full mock experiment (`integration.e2e_headless_experiment_smoke`
with `MIB_EXECUTION_PROVIDER=replay`) and `accounting_*` equals the fixture's frame counts.
Evidence: target-software (x86) then target-software (ARM, S6).

## S2. Profile compiler and readiness — 2 weeks

`src/backend/processing/pz/PzProfileCompiler.{h,cpp}`: `ProcessingConfig` + ROI 1/ROI 2 +
`p2m` + `EModulusLut` + `StorePolicy` -> `CompiledProfile { std::array<uint32_t,16> configWords;
std::array<uint32_t,32> page; std::vector<uint8_t> lut; }`.

| Source (`ProcessingConfig` / camera) | Destination |
|---|---|
| ROI 1 (camera geometry) | config word 0 `GEOMETRY` = width/height; sensor window via Aravis (S4) |
| `roi` (ROI 2, fixed 512x96) | config words 1-2 `ROI_ORIGIN`, `ROI_SIZE` |
| preview decimation (UI setting, default 200 at 5000 fps) | config word 5 `PREVIEW_DECIMATION` |
| trigger delay / `pulseDurationUs` | config words 6-7 in ticks (`timestamp_hz` from identity) |
| background generation | config word 4 `BACKGROUND_EPOCH` after `uploadTable(BACKGROUND)` |
| `gaussian_blur_size`, `morph_kernel_size`, `morph_iterations`, filter enables, `require_single_inner_contour`, target-group enables | page P0 (packed bytes and flag bits) |
| `bg_subtract_threshold`, `empty_frame_pixel_threshold` | page P1 |
| min contour area (10 px), border margin (2 px), `p2m` (Q16.16 um/px) | P2, P3, P4 |
| `area_threshold_min/max` (um2), `deformability_threshold_min/max`, `area_ratio_threshold_max`, `ring_ratio_min/max` | P5-P11 (Q16.16 / Q0.16) |
| `target_group.*` | P12-P17 |
| store policy: invalid every N, multi-image count, flags | P18 |
| LUT axes (area um2 min/step, deformability min/step) | P19-P21; grid bytes via `uploadTable(EMODULUS_LUT)` (200x200 x u16 Q8.8, 80 KB) |

Rejections at compile time (become readiness failures, gate `processing.profileCompile`): blur
size not in {3,5}; ROI 2 not 512x96 or outside ROI 1; values outside fixed-point range; LUT
coverage empty. New readiness gates: `provider.capability` (profile id/version and page size
match the compiler), `camera.frameRate` (configured vs achievable from the producer's
`AcquisitionFrameRate` max and `PzFrameRateLimitReason`; over-limit = Fail, shown with the reason).

**Tests**: `processing.pz_profile_compile_roundtrip` (compile -> decode -> equals the config within
fixed-point tolerance), `processing.pz_profile_reject_matrix`, readiness tests extended.
**Exit**: compiled words for the default profile match a fixture checked into the board repository
(the same bytes the PL simulation consumes). Evidence: target-software.

## S3. Recording on the instrument — 2 weeks

- Live: `ProviderFrame`s append rows to the existing `/valid_frames/metadata` and
  `/invalid_frames/metadata` compounds through `Hdf5Service` unchanged (chunk 100), keyed by
  `frame_id`; `accounting_*` from provider counters and record counts (TD-16 rule kept).
- After the run: `StoreDrainReader` (`src/backend/recording/pz/`, a C++ port of the board
  repository's `src/imx426/store_records.py`) walks the SSD store region (LBA range and record
  bytes from `STORE_*` registers via the provider), verifies CRCs, and appends `images`/`masks`
  (`MONO8` = ROI 1 frame, `MASK1` unpacked to uint8 ROI 2-sized) matched by `frame_id` to the
  metadata rows; multi-image frames go to `/valid_frames/series_images`.
- `/experiment_info` gains `software = "YOFO Studio <version>"`, `execution_provider`,
  `science_profile`, `profile_version`, `profile_id`, `pl_build_id`.

**Tests**: `recording.store_drain_reader` against the board repository's store fixtures;
`recording.pl_run_hdf5_layout` (file opens in review; counts equal `accounting_*`).
**Exit**: a replayed run produces an HDF5 that the desktop review opens. Evidence: target-software.

## S4. Preview camera through Aravis — 1.5 weeks (after the board's W4 spike)

Commit the WIP from `feat/aravis-framework` (`include|src/backend/camera/aravis/`, tests) with
these changes:
- Device selection by `MIB_ARAVIS_DEVICE_ID`, else the first device whose vendor is `YOFO`.
- Geometry and rate: `arv_camera_set_region` (ROI 1), `arv_camera_set_frame_rate`, read
  `AcquisitionFrameRate` max and the `PzFrameRateLimitReason` enumeration for readiness.
- `LatestFrame` delivery supported (preview semantics); `EveryFrame` remains for Overview.
- Timestamps from chunk data (`ChunkFrameID`, `ChunkTimestamp`) -> `timestampDescriptor()` =
  device ticks at `timestamp_hz`; the `frame_id` is carried into `Frame` so previews and records
  correlate.
- `CameraControlService` writes `ExposureTime`, `AcquisitionFrameRate`, `PzStrobe*` through
  `arv_device_set_*_feature_value`; the eGrabber script path is not used on the instrument.
**Tests**: existing 5 Aravis tests on the fake camera plus `camera.aravis_gentl_pattern`
(board-owned pattern producer on x86 through Aravis's GenTL consumer).
**Exit**: `AravisCamera` streams from the pattern producer at 25 fps on x86; then from the board
producer on the PS. Evidence: target-software, then physical.

## S5. Remote UI transport and rebrand — 3 weeks

**Server** `crates/mib-bridge-server` (Rust, tokio + axum + tokio-tungstenite): links
`mib-bridge` in-process; one WebSocket per client at `/ws`; text frames carry the existing JSON
event/command documents (`bridge-contract.json` `json_transport`, ABI 19) with a `request_id`
envelope for commands; binary frames carry frame packets unchanged (96-byte `MIBF` header);
`/` serves `desktop/dist`; a bearer token from `/etc/yofo-studio/token` on the query string.
Bounded frame pulls: the server sends a frame only after the client acknowledged the previous
one (the pull discipline of the current web view). Client loss (`ping` timeout 5 s) raises the
facade's controlled Stop & Save.
**Frontend**: `desktop/src/transport/{Transport.ts, tauriTransport.ts, wsTransport.ts}`; the
existing `invoke`/`listen` call sites go through the interface; `VITE_MIB_TRANSPORT=ws|tauri`.
Overview tab: ROI 1 rectangle plus the fixed ROI 2 box; live "achievable fps: N (limit: sensor
geometry | profile | store)" while ROI 1 changes; Apply disabled above the limit.
**Rebrand** (user-visible only): `desktop/src-tauri/tauri.conf.json` (`productName`, window
title, `identifier` `bio.yofo.yofo-studio`), `desktop/package.json` name, `desktop/index.html`
title, `App.tsx:2108`, Inno scripts `resources/installers/*.iss` (AppName, Publisher), update
publisher names, Sentry release prefix `yofo_studio@`, HDF5 `software` attribute. Unchanged:
CMake project/targets, `mib_processing_*`, `MIB_*`, `MIBF`.
**Tests**: server contract test replaying recorded event streams; frontend tests run against a
mock WS server; `frontend.review_parity` unchanged.
**Exit**: browser on the bench PC runs a full mock experiment against the backend on x86, then on
the PS. Evidence: target-software, then physical.

## Order and critical path

S7 -> S6 (needs the Yocto SDK from the board's W2) -> S1+S2 against fixtures (no hardware) ->
S3 -> S4 (after the board's producer spike) -> S5. S1/S2/S3/S5 can start on x86 immediately after
S7; only S4 and the hardware evidence wait on the board. The critical path to a first
instrument run is the board's PL classical profile, not this repository.
